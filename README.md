# RetailFlow: DevOps project

A small online store (product list, add product, buy, recent orders), built and delivered with a
complete DevOps toolchain: **Docker, Kubernetes, Terraform, GitHub Actions CI/CD, DevSecOps
scanning and the Render cloud platform**, with a public HTTPS link. Everything runs on free plans,
with no credit card needed.

```
                 ┌──────────────── Render.com (created by Terraform, free plan) ────────────────┐
 Browser ─HTTPS─►│ RetailFlow web service (Docker, Node.js) ──► PostgreSQL (managed database)    │
                 └──────────────────────────────────────────────────────────────────────────────┘
                                   ▲ "deploy commit <sha>" via the Render API
 git push ─► GitHub Actions: test ─► security scan ─► build + scan image ─► Kubernetes test ─► deploy
```

Locally the same app runs with Docker Compose (app + PostgreSQL + Caddy) or on Kubernetes.

## The website

| Page | What it shows |
|---|---|
| **Shop** | Product catalogue with categories and search, a cart, and "Place order". All products in the cart are reserved in one PostgreSQL transaction |
| **Orders** | All orders, and a page for each order with its items, total, customer and the server/pod that saved it |
| **Admin** | Revenue, orders, units sold, low-stock count, best sellers; add products, change stock, remove products |
| **How it's built** | Live status of this deployment (health, database latency, deployed commit, platform, server/pod, uptime), the CI/CD pipeline, and each DevOps part with links to its files |

The **Request log** bar at the bottom lists every API call the page makes, with its status, time and the server that answered.

## How each requirement is met

| Requirement | Marks | Where |
|---|---|---|
| **Microservices** | 3 | The app is an independent, stateless service with its own database, a REST API (`/api/products`, `/api/orders`, `/api/stats`, `/api/info`), a health endpoint and graceful shutdown. It runs as separate containers (app, database, proxy) that talk over the network, and it scales to several replicas on Kubernetes (`k8s/app.yaml`, 2 replicas). |
| **Docker** | 4 | `app/Dockerfile` (small Alpine image, non-root user, health check) and `docker-compose.yml` (app + PostgreSQL + Caddy, volumes, health checks). One command runs everything. |
| **IaC** | 2 | `terraform/main.tf` uses Render's official Terraform provider to create the cloud web service (built from `app/Dockerfile`) and a managed PostgreSQL database, and connects them. `terraform apply` / `terraform destroy`. |
| **Kubernetes** | 2 | `k8s/`: Namespace, Deployment (2 replicas, probes, resource limits, non-root), StatefulSet with a persistent volume for PostgreSQL, Services, and the password stored as a Secret. Tested automatically on every push in a temporary `kind` cluster. |
| **CI/CD** | 3 | `.github/workflows/ci-cd.yml`: test → security scan → build and scan image → Kubernetes test → push to GitHub Container Registry → tell Render to deploy that exact commit, wait until it's live, then test the live site. |
| **DevSecOps** | 2 | In the pipeline: **Gitleaks** (secrets in Git), **Trivy** (vulnerable dependencies, image scan, misconfigurations), **Dependabot** (`.github/dependabot.yml`). Plus: non-root containers, read-only filesystem on Kubernetes, secrets never in Git (the database password is generated by Render; API keys are GitHub secrets), HTTPS, security headers, input validation. |
| **Cloud** | 2 | **Render** (cloud platform as a service), free web service + free PostgreSQL in the Singapore region. The local machine (Docker Desktop) is also covered. |
| **Public link** | 2 | `https://retailflow-xxxx.onrender.com`, printed by Terraform. Render provides the HTTPS certificate. |

## Run it on your laptop (Docker)

Needs Docker Desktop.
```bash
cp .env.example .env
docker compose up --build
```
Open **http://localhost:8080**. Test it with `./scripts/smoke.sh`. Stop with `docker compose down`.

## Run it on Kubernetes (Docker Desktop)

1. Docker Desktop → Settings → **Kubernetes** → Enable Kubernetes → Apply.
2. Build the image, then deploy:
   ```bash
   docker build -t ghcr.io/shivamcp18/retailflow:latest app
   ./k8s/deploy.sh
   kubectl -n retailflow get pods
   ```
3. Open **http://localhost:8080**. Refresh a few times: the sidebar and the "How it's built" page show which of the 2 pods answered.

Remove it with `kubectl delete namespace retailflow`.

## Deploy to the cloud: Render (one time, about 10 minutes, no credit card)

**1. A Render account.** Sign up at https://render.com with **Sign in with GitHub**. The free plan needs no card.

**2. An API key and your workspace ID**
- Render dashboard → your avatar → **Account Settings** → **API Keys** → **Create API Key**. Copy it.
- Workspace ID: Render dashboard → **Workspace Settings**. The ID starts with `tea-`. Or run:
  `curl -s -H "Authorization: Bearer <API_KEY>" https://api.render.com/v1/owners`

**3. Create the cloud resources with Terraform**
```bash
brew install terraform                  # if you don't have it yet
cd terraform
export RENDER_API_KEY=rnd_xxxxxxxx
export RENDER_OWNER_ID=tea-xxxxxxxx
terraform init
terraform apply                         # type "yes"
```
It prints `service_id` and `website`. Render builds and starts the app the first time (about 3–5 minutes).

**4. GitHub secrets.** Repo → Settings → Secrets and variables → Actions → New repository secret:

| Secret | Value |
|---|---|
| `RENDER_API_KEY` | the API key from step 2 |
| `RENDER_SERVICE_ID` | the `service_id` from Terraform (starts with `srv-`) |

**5. Deploy.** Push to `main`, or Actions → CI/CD → **Run workflow**. The last job deploys the commit
and prints the live link in the run summary.

**Free plan notes:** the service sleeps after 15 minutes without visitors, and the first visit then
takes about a minute to wake it up. Open the link a minute before you demo it. The free database
is deleted after 30 days. Run `terraform apply` again to create a new one.

**When you're done:** `terraform destroy`.

## The pipeline, step by step

| Stage | What it does | Fails the build when |
|---|---|---|
| 1. Test | `npm ci && npm test` (unit tests in `app/test`) | a test fails |
| 2. Security scan | Gitleaks, Trivy dependency scan, Trivy config scan | a secret is committed, or a dependency has a CRITICAL vulnerability |
| 3. Build | `docker build`, Trivy image scan, push to `ghcr.io` (main only) | the image has a CRITICAL vulnerability |
| 4. Kubernetes test | creates a `kind` cluster, runs `k8s/deploy.sh`, runs `scripts/smoke.sh` against it | the app doesn't work on Kubernetes |
| 5. Deploy | calls the Render API to deploy this commit, waits until the deploy is `live`, then runs `smoke.sh` against the public URL | the deploy fails or the live site doesn't work |

The website's sidebar and the "How it's built" page show the running version (the commit SHA), so you can prove that a new push was deployed.

## Quick answers for the viva

- **Why Docker?** The app and all its dependencies run the same way on any machine: the laptop, CI and the cloud.
- **Docker Compose vs Kubernetes?** Compose runs all the containers on one machine (the laptop). Kubernetes adds replicas, self-healing (liveness and readiness probes), rolling updates and Secrets, and is tested in CI on a real cluster.
- **What does Terraform give us?** The cloud setup (web service + database + how they connect) is described in code: repeatable, reviewable, and removable with one command.
- **Why Render?** It's a cloud platform (PaaS) with a free plan that needs no credit card. It runs our Docker image and gives HTTPS automatically.
- **Where are the secrets?** Never in Git. Render generates the database password and Terraform passes it to the app. On Kubernetes it's a Secret. GitHub keeps the Render API key as an encrypted secret.
- **What is DevSecOps here?** Security checks run automatically in every pipeline run (shift left): leaked secrets, vulnerable libraries, image vulnerabilities and misconfigurations block the release.
- **How does HTTPS work?** In the cloud, Render provides the certificate for the `onrender.com` address. Locally, Caddy is the reverse proxy and can get Let's Encrypt certificates for a real hostname.
